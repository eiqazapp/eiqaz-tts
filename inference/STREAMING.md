# Eiqaz TTS — التوليد المتدفق والمقاطعة وثبات النبرة (Streaming)

واجهة التدفق المباشر فوق مسار الإنتاج R1F نفسه: نص يصل تدريجيًا (من LLM
مثلًا) ← صوت يبدأ فور جاهزية أول جملة آمنة، مع إمكانية المقاطعة في أي
لحظة، وثبات هوية المتحدث والنبرة عبر المقاطع — **بلا أي تعديل في
النموذج أو الأوزان أو الترميز أو قواعد النطق** (الوحدة `stream_tts.py`
تستورد `infer.py` كما هو).

---

## 1) المعمارية

```
LLM / مصدر النص (تدفقي)
        ↓  stream.feed(text)             — نص جزئي في أي لحظة
مخزن نص آمن (Text Buffer)               — لا توليد قبل حد آمن
        ↓
مجزّع واعٍ بالنبرة (Prosody-aware Chunker)
    نهاية جملة (. ! ؟ ? …) ← فواصل ناعمة (، ؛ ; :) ← حدود كلمات (ملاذ أخير)
    + دمج الجمل القصيرة حتى 144 توكن (فلسفة PATCH 14)
        ↓
معالجة R1F الموحدة (infer.prepare_text_rich)   — بلا مساس
        ↓
R1F (MixerTTS · states_cont_180516.pth)
    نفس speaker ID + emotion=0 + pace لكل مقطع (conditioning متطابق)
        ↓
المُصوِّت vocos22.onnx (نفس denoise=0.005)
        ↓
استمرارية صوتية سببية (Trim → مرساة RMS جارية → تلاشي 8ms → فاصل 0.2s)
        ↓
Audio Queue (لكل طلب request_id خاص)
        ↓
المستهلك (Consumer) — أي منصة: CLI / سطح مكتب / متصفح / أندرويد
```

**لماذا التدفق على مستوى المقاطع وليس داخل المقطع؟** MixerTTS غير ذاتي
التراجع (non-autoregressive): يقرأ توكنات المقطع كاملة ويتنبأ بالمدة
والنبرة ويولّد الميل دفعة واحدة. لا يوجد في المعمارية أي state صوتي أو
latent يُحفظ بين النداءات، ولا يوجد مخرج جزئي داخل النداء الواحد — لذلك
وحدة التدفق الطبيعية = جملة/مقطع كامل، وهو نفس ما دُرّب عليه النموذج
(وحدات متعددة الجمل حتى 160 توكن). التدفق هنا **حقيقي وليس زائفًا**:
أول AudioChunk يُنتَج ويصل المستهلك قبل اكتمال تغذية النص وقبل
استدعاء `finish()` — مثبت باختبار B (§31).

## 2) واجهة التدفق (Streaming API)

```python
from stream_tts import EiqazStreamingTTS, PlaybackQueue

tts = EiqazStreamingTTS()                 # يحمّل R1F مرة واحدة (checkpoints/states_cont_180516.pth)

stream = tts.create_stream(               # طلب جديد — request_id تصاعدي
    speaker=0,                            # 0 ذكر مصري / 1 أنثى (نفس خريطة الإنتاج)
    dialect='egy',                        # 'egy' أو 'msa'
    diacritize='auto',                    # auto/egyptian/fusha/manual — يُحسم مرة واحدة للطلب كله
    pace=1.0, denoise=0.005,              # نفس معاملات المسار الموحد
    min_chunk_tokens=12,                  # انتظار دمج الجمل القصيرة (فوق هذا تُطلق فورًا)
    max_chunk_tokens=144,                 # 90% من سقف التدريب (سياسة PATCH 14)
    chunk_gap_s=0.20,                     # فاصل الصمت بين المقاطع
    apply_continuity=True,                # معالجة الاستمرارية الصوتية
)

stream.feed('بص يا عمر،')                 # نص متدفق — 0..N مرة
stream.feed(' القسمة معناها إننا بنوزع الحاجة بالتساوي.')
stream.finish()                           # انتهى النص — اشطف الباقي

for ev in stream:                         # المستهلك — أي منصة
    if ev.is_audio:                       # AudioChunk
        play(ev.wave)                     # float32 mono @ 22050Hz
        # ev.request_id / ev.seq / ev.duration_s / ev.is_final / ev.n_tokens
    else:                                 # StreamEnd: kind = end|cancelled|error
        break
```

كل `AudioChunk` يحمل: `request_id`, `seq` (ترتيبه في الطلب), `wave`
(float32 أحادي 22050Hz), `sample_rate`, `n_tokens`, `duration_s`,
`synth_time_s`, `t_ready`, `text` (نص المقطع الخام), `is_final` (أفضل
جهد — الإشارة القاطعة للنهاية هي StreamEnd), `gain_applied`,
`trimmed_s`.

`stream.stats` يعيد لقطة إحصاءات: `ttfa_s`, `rtf`, `n_chunks_emitted`,
`n_chunks_consumed`, `n_discarded_inflight`, `synth_time_total_s`,
`audio_duration_total_s`, توقيتات المراحل، وحقل لكل مقطع.

**عقد LLM المستقبلي (§26):** أي مصدر نص متدفق يستدعي
`feed()/finish()` — طبقة الأوركسترا تستطيع إيقاف السلسلة كلها عند
المقاطعة (إلغاء stream الـTTS + إيقاف توليد الـLLM + إيقاف التشغيل).

**عقد المتصفح المستقبلي (§27):** النواة غير مرتبطة بأي واجهة أو نظام
تشغيل — المستهلك يستقبل AudioChunk (موجة + معدل عينة + request_id)
ويعزفه بنفسه. `PlaybackQueue` هي مرجع Python لمستهلك كامل؛ مثيل المتصفح
يطبق نفس العقد (submit + interrupt + epoch) عبر WebSocket.

## 3) واجهة المقاطعة (Interrupt API)

```python
stream.cancel()          # في أي لحظة — idempotent
```

عند `cancel()` يحدث **كل** التالي (بالترتيب):

1. **Stop future generation** — علم إلغاء يُفحص قبل كل مرحلة؛ لا مقاطع
   جديدة تُنتَج للطلب الملغى.
2. **Cancel/discard inference الجاري** — جارٍ `torch` لا يمكن قطعه من
   بايثون؛ يُستكمل ثم **يُهمَل ناتجه** ويُحصى في
   `stats['n_discarded_inflight']` — هذا هو الفرق الموثق صراحة بين
   «إلغاء حقيقي» و«إبطال نتيجة» (§25). في الممارسة: ≤ ثوانٍ قليلة
   (استدلال CPU سريع — RTF≈0.06).
3. **Clear Audio Queue** — كل AudioChunk منتظر يُحذف فورًا (تفريغ ذري
   تحت القفل — لا سباق مع المستهلك).
4. **Stop Playback** — مسؤولية المستهلك؛ `PlaybackQueue.interrupt()`
   (المرجع) يوقف التشغيل الجاري خلال ≤ 50ms (جيل عدّي: بدء طلب جديد
   لحظة المقاطعة لا يُحيي التشغيل القديم).
5. **Invalidate old stream** — طلب جديد يأخذ request_id أعلى؛ أي chunk
   بمعرّف قديم يصل المستهلك يُرفض (`PlaybackQueue.submit` → `stale`).

المستهلك المحجوز يستيقظ على `StreamEnd(kind='cancelled')` خلال ≤ زمن
الاستدلال الجاري. طلب جديد بعد المقاطعة **بلا إعادة تحميل النموذج**
(المحرك يُحمَّل مرة واحدة ويخدم الطلبات المتعاقبة — اختبار F).

سيناريوهات السباق الستة (§18) مختبرة كلها (اختبارات G1-G6): جاهزية +
مقاطعة متزامنان · مقاطع مولدة قبل التشغيل · أثناء التشغيل · نتيجة
متأخرة بعد طلب جديد · مقاطعات متكررة · مقاطعة + طلب فوري.

## 4) ثبات هوية المتحدث (§7)

- **بالبناء:** كل مقاطع الطلب الواحد تمر بنفس `model.infer(...,
  speaker=S, emotion=0, pace=P)` — الـconditioning متطابق حرفيًا
  (speaker_emb نفسه)، فالصوت واحد بالتعريف على مستوى النموذج.
- **بالقياس (اختبار H):** F0 median لكل مقاطع الرد داخل مدى < 60Hz
  (نفس معيار القسم G في test_pipeline) · ECAPA (مركز الرد): متوسط
  تشابه المقطع-إلى-المركز ≥ 0.75 و min ≥ 0.50، بينما العابر (ذكر ضد
  مركز أنثى) ≤ 0.40 — فجوة تمييز قيست فعليًا.
- كل المقاطع تستخدم نفس: speaker ID · لهجة · وضع تشكيل (يُحسم مرة
  واحدة من أول نص) · pace · denoise.

## 5) ثبات النبرة والأسلوب (§8/§9) — وما هو ممكن فعلًا

ما يملكه النموذج (فُحص في الكود): speaker conditioning ✓ · emotion
embedding (يربك — الإنتاج دائمًا 0، لا يُستخدم) · pitch_mean/std مثبتة
في checkpoint ✓ · تنبؤ مدة/نبرة لكل توكن. ما **لا** يملكه: reference
audio conditioning · style encoder · latent acoustic state · prosodic
state قابل للحفظ — **ولا يوجد أي state صوتي بين النداءات**.

الاستراتيجية المطبقة (بلا معالجة زائفة — ليست مجرد تطبيع جهارة):

1. **Conditioning متطابق** لكل المقاطع (أعلاه) — نفس شخصية الصوت
   والطبقة والأسلوب العام.
2. **تجزئة واعية بالنبرة:** الحدود عند نهايات الجمل (حيث إعادة ضبط
   الإعراب طبيعية أصلًا حتى في الكلام البشري) + دمج الجمل القصيرة
   حتى 144 توكن (PATCH 14: كل حد مقطع يصفّر نبرة الجملة — مقاطع أطول
   = صفريات أقل = إحساس «شخص واحد مستمر») + الجملة العملاقة تُقسم عند
   الفواصل الناعمة أولًا.
3. **استمرارية صوتية سببية** (نسخة streaming من PATCH 13 — بلا معرفة
   المستقبل): قص صمت الحواف المتغير → مرساة جهارة RMS جارية بكسب
   محدود [0.5, 2.0] ومرساة تتكيف ببطء (EMA 0.15) → تلاشي 8ms عند
   حافتي الكلام → فاصل صمت ثابت 0.2s قبل كل مقطع (عدا الأول) → أمان
   ذروة. الوصل دائمًا «صفر ← صمت ← صفر» — النقرات مستحيلة بالبناء
   (قيس: أقصى قفزة عند الوصلات = 0.0).
4. **رفض صريح لسياق/تراكب النص (§10):** لا يمكن إدخال سياق نصي مجاور
   في استدلال النموذج دون توليد صوت للسياق نفسه (مكررًا)، وقصّه صوتيًا
   غير متوافق (تنبؤ المدد ≠ محاذاة دقيقة) — خطر تكرار/بتر فونيمات
   صريح في المواصفة. لم يُستخدم، وموثق هنا كقرار.

**النتيجة المقيسة (نص §22 الكامل — سؤال/خبر/تعليمي/فاصلة/جملة طويلة/
انتقال مصرية→فصحى/شدة/{ق}/{ج}/{ء}):** مدى F0 = 29Hz · نسبة RMS بين
المقاطع = 1.10 · CV معدل الكلام = 0.03 · لا قفزة F0 متجاورة > 21Hz ·
نبرة السؤال ترتفع طبيعيًا (179Hz مقابل 155 للخبر — سلوك نموذج سليم
وليس عدم ثبات) · هوية ECAPA عبر حد اللهجة min = 0.66.

## 7) التوافق والمسار الإنتاجي — إثبات بالبايت

- **بلا تعديل على infer.py / webapp.py / CLI** — كلها تعمل كما هي
  (اختبار J + 54/54 + 14/14 القائمة).
- **bit-identity (اختبار I2-أ):** بتوقيف معالجة الاستمرارية
  (`apply_continuity=False`)، موجة كل مقطع من التدفق **متطابقة
  بايت-ببايت** مع `infer.synthesize` لنص المقطع نفسه — أقوى إثبات أن
  التدفق يستخدم مسار الإنتاج نفسه بلا أي تغيير في النطق.
- **توكنات النطق (I2-ب):** تسلسل توكنات التدفق (كل المقاطع) يطابق
  single-shot للنص الكامل بعد استبعاد توكن `_eos_` — لكل مقطع نهاية
  تسلسل خاصة (وحدة توليد مكتملة)؛ لا فرق في توكنات الكلمات نفسها.
- **المكافئ الصوتي (I2-ج):** التجميع المتدفق (مع الاستمرارية) مقابل
  single-shot لنفس الجملة: ECAPA = 0.978 · ΔF0 ≈ 5Hz · نسبة RMS ≈ 1.07 ·
  فرق المدة ≈ 5%.

## 8) القيود الحقيقية (حدود صادقة — §34)

1. **لا streaming داخل المقطع:** النموذج غير ذاتي التراجع؛ أصغر وحدة
   تسميع = جملة/مقطع كامل. أول صوت لا يسبق اكتمال **أول جملة آمنة**
   (وليس أول كلمة) — في المحادثة هذا هو السلوك المرغوب أصلًا.
2. **إعادة ضبط الإعراب عند حدود المقاطع:** النبرة داخل كل مقطع
   طبيعية ومتصلة، والحدود عند نهايات جمل (طبيعية)، لكن لا يوجد
   « prosody phrase-level» متصل عبر المقاطع — لا يوجد state للنموذج
   أصلًا يحفظه. التخفيف: الدمج حتى 144 توكن + الاستمرارية السببية.
3. **إلغاء الاستدلال الجاري:** لا يمكن قطع نداء torch من بايثون؛
   النتيجة تُهمَل وتُحصى (`n_discarded_inflight`) — كشف لا ادعاء.
4. **تشكيل بجرالة الجملة:** التشكيل التلقائي (catt+det) يعمل على كل
   مقطع؛ في حالات نادرة قد تختلف حركة كلمة عند حد الجملة عما لو شُكّل
   النص كاملًا (التشكيل الجُملي أقرب للطبيعي أصلًا لأن الجملة مكتملة).
5. **عرض الجلسة الواحدة = متحدث واحد:** هوية الصوت تثبت داخل الطلب؛
   تغيير المتحدث = طلب جديد (request_id جديد).
6. **أول مقطع بعد إقلاع المحرك أبطأ** (تسخين استدلال ~0.5s إضافية) —
   تُلاحظ في TTFA للطلب الأول فقط.

## 10) جسر المتصفح — التفعيل الفعلي داخل webapp.py (PATCH 18)

المحرك (الأقسام 1–9) واجهة مكتبة. **webapp.py يفعّله فعليًا** عبر نقطة
نهاية WebSocket على نفس الخادم — بلا أي مكتبة جديدة (تنفيذ RFC 6455
مبسّط بمكتبات بايثون المدمجة):

```
المتصفح (web/index.html)                       webapp.py (/ws)
─────────────────────────                       ─────────────────────────
«توليد الصوت» (وضع البث مفعّل)
  │  start {speaker, dialect, diacritize,       │ create_stream(cancel_
  │         pace, denoise}          ──────────► │   previous=True) → محرك
  │  started {request_id, sample_rate} ◄─────── │   R1F المشترك (تحميل واحد)
  │  feed "3 كلمات" كل ~40ms        ──────────► │ stream.feed(...)
  │  chunk {seq, n_samples, text...} ◄───────── │ AudioChunk جاهز
  │  [إطار PCM16 ثنائي]             ◄───────── │ ← فور جاهزيته
  │  ▶ جدولة Web Audio فورية                     │
  │    (t_next متواصل: بلا فجوة/تراكب)           │ (يستمر توليد البقية)
  │  finish                          ──────────► │ stream.finish()
  │  end {kind, stats}               ◄───────── │ StreamEnd
  │
  «إيقاف ومقاطعة» أو طلب جديد
  │  interrupt / start جديد          ──────────► │ cancel() + تفريغ الطابور
  │  ▶ hard stop لكل المصادر المجدولة            │ + رفض المتأخر (request_id)
```

**عقد الخادم للتكامل المستقبلي (LLM حقيقي §26):** أي مصدر نص متدفق
يستبدل محاكاة القطع في الواجهة (إرسال كل ~40ms) بنداءات `feed/finish`
حقيقية — الخادم لا يتغير إطلاقًا.

**المقاييس المثبتة من متصفح حقيقي (Chromium):**

| القياس | القيمة |
|---|---|
| أول صوت (TTFA من النقرة) | 190ms — عند **15.6%** فقط من النص |
| مقاطع شُغّلت فعليًا (onended) | 16/16 |
| أقصى فجوة/تراكب جدولة | 1ms (تقريب القياس) |
| اتساق الجهارة عبر المقاطع (RMS ratio) | 1.096 |
| مقاطعة → صمت | فورية (hard stop) + end cancelled |
| طلب جديد فور المقاطعة | يعمل — 16 مقطعًا سليمة |
